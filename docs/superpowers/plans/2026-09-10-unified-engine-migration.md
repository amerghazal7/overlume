## USER DECISION (verbatim — this is the epic's charter)

> "a new decision to migrate everything implemented in the rendering node to the new engine so we have on node one view and we can swith the mode between all modes and everything use the same rendering engine, if the plan doesn't account for that, let's consider this and make it our next big thing and most important to get done"

Every task below exists to satisfy this literally: **one node, one Filament-backed engine, a local switch between all three modes.** Where a cheaper option would satisfy "one node" but not "same engine" (Research §4 Option C — keep CUDA as a Filament-fed texture), it is named and rejected, not silently taken.

**Goal:** Retire `micropilot_rendering_node`'s CUDA reprojector entirely. `micropilot_visualization_node` (already Filament/mode-3-native) grows modes 1 (bowl) and 2 (pointcloud-hybrid), rendered through the exact same `visual_renderer` engine mode 3 already uses, then becomes the only rendering process; the two-node mux (ADR-0002) is deleted once parity is signed off.

**Architecture:** Bowl reprojection — today a hand-written CUDA rasterizer (`reproject.cu`) — moves to a Filament mesh + material: camera projection/distortion math is ported to portable host C++ once (TDD'd standalone), used to bake per-vertex, per-camera UV+blend-weight vertex attributes on the CPU whenever bowl config changes, and a small multi-texture-sample fragment shader does the per-pixel blend GPU-side — the same "rasterizer does the projection" idea the research inventory names as CUDA's whole reason for existing (§1.12) minus the reimplementation. Camera pixels cross the clang/libc++ POD boundary via a dedicated `set_camera_frame()` entry point (Research §4 Option B), not a `SceneGraph`/`set_scene()` field, because they are a new *size class* the existing deep-copy staging buffer was never built for. Robot self-view/proxy compositing stops being a bespoke z-buffer kernel and becomes "add the already-Filament-native ego mesh to the same scene as the bowl" — Filament's own depth test does the compositing for free. Mode 2 becomes "mode 1's bowl, plus the already-shipped `PointCloud` layer (VM-035), colorized by a new node-side adapter" — no new library rendering code at all.

**Tech Stack:** Filament 1.56.5 (pinned, ADR-0001), the existing `visual_renderer` clang/libc++ static archive + POD boundary (ADR-0003), `micropilot_visualization_node` (gcc/libstdc++), CycloneDDS with the shared-memory transport fix already in production for 6-camera ingest.

**Spec:** No prior spec document covers this — the research inventory reproduced in full context above (2026-09-10 research pass) *is* this plan's spec; every Decision below cites it by section (`§N`) alongside live path:line re-verification.

## Decisions (grounded in the research inventory + re-verified live, 2026-09-10)

### 1. Migration order is risk-ranked: bowl (mode 1) → self-view/robot-proxy → node consolidation → hybrid (mode 2) → cutover

Per the research's own §8: mode 1 is the whole existing product surface (mode 2 degrades to it with nothing else), has the clearest Filament-equivalent shape (project N textured views onto one mesh — a GL rasterizer's native job), and its perf risk is boundable with dirty-tracking precedent that already exists (`img_dirty_`, `rendering_node.hpp:220`, `.cpp:769-786`). Self-view/robot-proxy compositing reuses mode 1's texture path and is lower-stakes (cosmetic, already optional/off-by-default, `rendering_node.cpp:80-84`). Node consolidation (the mux-facing plumbing) is scheduled *before* mode 2 deliberately: it lets Task 5's camera-colorization adapter reuse the same live camera images Task 2 already ingested, instead of a second ingest path. Mode 2 is scheduled last of the rendering tasks because its camera-colorization gap (research §2, §7.3) has no current Filament precedent and should not block "one node, modes 1+3 working" from shipping first — **do not attempt bowl and hybrid simultaneously**, restated verbatim from the research's own recommendation.

### 2. The POD-boundary camera-texture mechanism: Option B (`set_camera_frame()`), not A or C — and one sub-question stays a real user decision

Research §4 laid out three options. Re-argued here with the numbers re-derived, not just cited:

- **Option A (a `CameraImagePlane[]` SceneGraph category)** would make `set_scene()`'s deep-copy staging buffer (`scene_buffer.cpp:7-103`) `std::vector::assign()` ≈1280×720×3×6 ≈ 16.6 MB into **two** double-buffered slots every tick the images change — at 30 Hz, ~1 GB/s of CPU memcpy for staging *alone*, before any GPU upload, against a buffer class whose largest current occupant (OGM cells) is a couple of small single-channel grids (`ground_grid.cpp:157-161`). Rejected: wrong entry point for this size class.
- **Option C (keep the CUDA reprojector, feed Filament one composited RGBA image)** sidesteps the whole texture-upload question but does not migrate anything — it keeps CUDA in the loop under a different label. Rejected outright: it fails the user's literal charter ("everything use the same rendering engine").
- **Option B (`set_camera_frame(VisualRenderer*, uint32_t cam_idx, const uint8_t* rgb, uint32_t width, uint32_t height, uint64_t frame_id)`)** is the same shape as `set_ego_model()` (`ego.cpp:106-186`) and `set_environment_source()` (Epic 4 Decision 2) — a POD entry point outside `SceneGraph`, for content that doesn't belong in the per-tick deep-copied buffer. It pushes straight to a persistent `filament::Texture` via `Texture::Builder()...setImage()` — the exact call `ground_grid.cpp:138-161` already uses for OGM textures — with **per-camera dirty tracking** (skip `setImage()` when the caller-supplied `frame_id` hasn't changed since the last upload for that camera — an O(1) integer compare, not a content re-derivation) in the same spirit as `img_dirty_` (`rendering_node.cpp:769-786`), sized correctly for a 6x1280x720x3 (~16.6 MB) production frame rather than a content memcmp at that size (Task 1 Step 2). **Decision: Option B.**
- **Ruled out alongside A/C: `filament::Stream`/`Texture::setExternalStream`/`setExternalImage` (`Texture.h:420-470`) as a way to hand Filament the camera pixels without a POD-boundary copy at all.** Not viable on this target: `Stream.h:41-42` documents the two supported configurations as ACQUIRED (an Android `AHardwareBuffer`) and NATIVE (an Android `SurfaceTexture`) — both Android-platform primitives, not available on this Linux/EGL build. This is exactly the evidence that makes Option B's explicit-copy-through-`api.h` the correct call here, not merely the simplest one.
- **Weighed against Option B as shown above (plain-copy `set_camera_frame`): Option B-zero-copy, a release-callback variant of the same entry point.** `filament::backend::BufferDescriptor` — the base class `PixelBufferDescriptor` inherits, and the type `Texture::setImage()` actually consumes — defines `using Callback = void(*)(void* buffer, size_t size, void* user)` (`BufferDescriptor.h:50`) and a `(buffer, size, callback, user)` constructor (`BufferDescriptor.h:92-95`) that takes the buffer **by reference, not by copy**, releasing it via that POD function pointer once the driver has consumed it — this is precisely `ground_grid.cpp:149-161`'s own upload pattern already exercises (its `heap`/`user` there is a `new std::vector<uint8_t>` the callback deletes; nothing requires that particular ownership shape). Both the function pointer and the `void*` are POD, so this crosses `api.h` cleanly, same as every other pointer/dimension tuple in this codebase. Signature: `set_camera_frame(VisualRenderer*, uint32_t cam_idx, const uint8_t* rgb, uint32_t width, uint32_t height, uint64_t frame_id, void (*release)(void*, size_t, void*), void* user)` — the node passes a `release` that drops the captured **converted RGB buffer** (the `cv_bridge::CvImagePtr`/`cv::Mat` Task 2 Step 6's ingest produces — NOT the `sensor_msgs::Image::SharedPtr` itself; see the honest framing below) once Filament calls it back, and `nullptr` for `release` keeps today's copy-on-call contract (the library heap-copies exactly like `ground_grid.cpp` does) for tests and any caller that doesn't want to manage a capture's lifetime. **Honest framing — this decision is one copy vs. two, not zero vs. one.** Task 2 Step 6's own ingest path decodes every frame via `cv_bridge::toCvCopy(msg, "rgb8")` (`rendering_node.cpp:405-419`, explicitly reused) — an unconditional full-size conversion copy into a new `cv::Mat`, which stays on the critical path in **both** variants; the buffer handed to Filament is that `cv::Mat`'s heap, not the SHM message's, so "the SHM transport already has the bytes in shared memory" buys the release-callback shape nothing by itself. What release-callback eliminates is only the **library-side** `setImage()` heap copy — the plain-copy path's ~16.6 MB heap-copy-and-free per dirty tick (6×1280×720×3, at 30 Hz when all 6 cameras are dirty), the same class of cost Option A was rejected for above, just moved from `set_scene()`'s staging buffer into `set_camera_frame()`'s upload path. Plain-copy = convert + library heap copy (two full-size copies per dirty frame); release-callback = convert only (one), the converted `Mat` handed to Filament and deleted in the callback. **One checkable fact to gather before the USER DECISION below: the actual wire encoding on the six `raw_images` topics** (the fixture bag `stack_v2_full_sensors_2026-09-09` and the robot's own drivers — the bag's `metadata.yaml` records only the message type, not the `encoding` field, so peek one message). If they are already `rgb8`, `cv_bridge::toCvShare` (no conversion) plus capturing the `Image::SharedPtr` itself in `release`/`user` achieves the true zero-per-tick-memcpy this bullet's earlier draft claimed unconditionally — put that on the table as a third option at the same decision point; if not, `toCvShare` degrades to a copy internally and "one copy vs. two" is the whole decision.

**The one thing genuinely left open (flagged, not silently resolved, per the task instructions):** the historical GL renderer's own regression (`docs/superpowers/specs/2026-06-23-gl-optimization-design.md:11-24`) shows a ~35% fps hit (~38 fps measured vs. the >60 fps target, RTX 3090) — but that figure bundles **reupload + per-camera uniform re-sets + full-frame framebuffer readback to NumPy measured together**, per the doc's own summary; the per-frame NumPy readback has no counterpart on the Filament path (the merged node's existing budget rows already carry `render_frame`'s own readback), so reupload alone was NOT the whole hit and the ~35% is an inflated upper-bound analogy, not a reupload cost to judge the first Filament-side number against. Dirty-tracking bounds the *reupload* cost (a camera whose image hasn't changed this tick costs nothing), but says nothing about the *projection* cost once 6 live textures ARE dirty every tick during normal driving. **Task 2's Step 5 perf gate is the first real measurement of this** — nobody has run it, on either box (research §5). If that gate misses budget, the fallback is coarser per-vertex UV baking (larger dirty-skip windows, lower bowl tessellation) before falling back to Option C's "cheat," which stays available but unused unless Task 2's own review gate calls for it explicitly. **This tradeoff — vertex-baked UV/blend (this plan's design, §3 below) vs. true per-pixel shader-side backward sampling closer to CUDA's exact fidelity — is the one open item this plan marks as a USER DECISION at the Task 2 review gate**, because the research's own honest-unknown #5 (distortion handling) was never resolved and a visual-fidelity-vs-complexity call belongs to the person who judges the bowl by its visuals (per this project's documented working style). **A second, independent open item joins it at the same gate, settled no later than Task 1 Step 0 (before Step 1 writes `set_camera_frame`'s implementation): plain-copy `set_camera_frame` vs. the release-callback `set_camera_frame` (Option B-zero-copy) above — decided on the honest one-copy-vs-two framing, with the wire-encoding check (the conditional third option, `toCvShare` + `Image::SharedPtr` capture) gathered first.** If plain-copy ships, Task 2 Step 5's perf gate carries the second ~16.6 MB/tick memcpy explicitly as its own CPU-side budget line (it does — Step 5's budget text names both the always-present conversion copy and the plain-copy-only second copy as separate line items) and ADR-0005 (Task 1 Step 4) must say in so many words why that copy is accepted here after being rejected there. If the release-callback shape ships instead, Task 1 Step 0's fixture and every `set_camera_frame` call site in this document passes `nullptr` for both new parameters (the degenerate, copy-on-call case), and only Task 2 Step 6's node wiring — the first real caller with a converted `cv::Mat` (or, under the third option, an `Image::SharedPtr`) worth capturing — supplies a real `release`/`user` pair.

**Correction to an earlier draft's premise:** camera *intrinsics/distortion* are not a "rarely-changing, GUI-tunable param" like bowl radius — they are not a ROS parameter at all. `rendering_node.cpp:263-265` declares only `image_topics`/`info_topics`; `K`/`dist` arrive asynchronously per camera on that camera's `CameraInfo` topic (`rendering_node.cpp:439-443`), at a time this node cannot predict or gate on `on_activate()`. Camera *extrinsics* (rig geometry) and the bowl shape params genuinely are ROS parameters (`rendering_node.cpp:181,71-88`) and genuinely are GUI-tunable-but-rare. Task 1/2's design (below) treats these as two different arrival models, not one.

### 3. Bowl rendering mechanism: vertex-baked per-camera UV + blend weight, GPU does the multi-texture blend

The CUDA kernel (`reproject.cu`) is a **backward** sampler: for every output pixel on the bowl surface, compute which camera(s) see it and sample their (distorted) pixel. A Filament rasterizer naturally wants the **forward** direction instead: for every bowl-mesh **vertex**, compute its UV in each camera's (distorted) image once, on the CPU, whenever bowl *shape* changes (`bowl_R0`/`k`/`Rmax`/mesh tessellation — genuinely rare, param-driven) or a camera's *calibration* changes (extrinsics param edit via the GUI bridge, `tools/vcam_ws_bridge.py:62-67`, or a new/changed `CameraInfo` message — see the addendum below for why this is not "rare"), bake those UVs + a per-camera blend weight (feather-margin-based, matching `blend.cuh`'s existing feather math) as vertex attributes, and let the fragment shader sample up to N camera textures per vertex-interpolated UV and blend by weight. This is coarser than CUDA's per-pixel backward sample (fidelity bounded by bowl-mesh tessellation density, an implementer's call tuned against the golden comparison), but it is the shape every other GPU-rasterized texture-projection problem takes, and it entirely avoids doing lens-distortion math inside a fragment shader (an unresearched, higher-risk path per research §7.5). The camera projection + plumb_bob distortion formula itself is ported to portable host C++ once (Task 2 Step 0) — reusable by the vertex baker (Task 2) and the lidar colorization adapter (Task 5), one implementation, two call sites, matching this codebase's own "two small copies, one per toolchain" precedent (Epic 4 Decision 5) — except here it is the **same** toolchain (host C++) on both sides, so it is one copy, not two.

**Frame convention (binds Tasks 1/2/3/5): bake and colorize entirely in RIG frame; the bowl is rig-frame geometry, anchored into the map-frame scene by the ego transform, per tick.** Every input to the bake and to Task 5's lidar colorization is rig-frame: `CameraExtrinsics` is rig-frame (Task 1's Interfaces), the bowl mesh is generated in rig frame (robot at its origin), `ProjectToCameraUv` takes a rig-frame point (Task 2's Interfaces), and Task 5 colorizes the cloud **after** `pointcloud_transform` (cloud→rig, `rendering_node.cpp:91-97` — its own comment says exactly this). The merged node's Filament scene, however, is map-frame with a moving ego: `render_frame` re-derives the ego entity's transform from the active scene every call (`renderer.cpp:1497-1501` → `update_ego_transform`, `ego.cpp:188`, fed by `EgoState` — map-frame position + heading, `scene.h:47-52`). The bowl joins that scene the same way: `update_bowl` (Task 2's `renderer.cpp` hook) sets the bowl entity's `TransformManager` transform to the **same** `r->scene_buffer.active().ego` pose each `render_frame` — identical source as `update_ego_transform`, so Task 3's ego-over-bowl depth compositing stays aligned wherever the robot is on the map, and `ego.valid == 0` snaps the bowl to the map origin (same convention as `update_ground_grid_transform`). Task 5's adapter transforms its colorized points rig→map by the same node-side ego pose the node feeds `set_scene()` before emitting `PointCloudPoint` (whose documented frame is map, `scene.h:161-163`). Mode-1/2 vcam presets are ego-anchored via the merged node's **existing** ego-anchored vcam path (`compose_ego_anchored_pose`, `visualization_node.cpp:872` / `ego_anchor.hpp:40`), so the view follows the robot exactly as the CUDA node's rig-frame vcam did.

**Addendum — per-tick extrinsics is real, and the static bake alone does not cover it.** `rendering_node.cpp:735-793` calls `reprojector_->set_cameras(scaled_params)` on **every** render tick, not on config-change: each camera's extrinsics is advanced by `compensate(cam_params_[i], up_stamps_[i], t_max)` whenever odometry is flowing (the ego-motion fix that exists because ~80 ms of camera phase spread bakes ~0.5 m of travel into a stitched frame while driving), per the source's own comment at that call site — *"the GUI tunes extrinsics live even while the image set is frozen ... the vcam/K may change any tick."* A full CPU vertex re-bake every tick (6 cameras × the bowl's vertex count × the projection+distortion math) is not the "expensive, rare operation" this plan can assume. **Chosen mechanism (stated implementably — the bake produces UVs and weights, not rays, so there is no "baked ray" for a uniform to transform):** the static bake keeps producing the per-camera **weights and camera-slot indices** (the per-triangle-uniform-index rule below, unchanged — coverage/seam topology doesn't move with ego-motion's centimetre-scale deltas), but the **UV is not baked**: the vertex shader recomputes it each frame from the mesh's rig-frame position (the ordinary position attribute) as `project(ego_motion_delta[cam] * position)`, with per-camera `K`/plumb_bob-distortion uniforms (uploaded by `set_bowl_config`, re-uploaded on each re-bake) plus the small per-camera 4×4 ego-motion delta uniform (updated per tick via Task 1's `set_camera_motion_delta()` — the cheap per-tick entry point this mechanism requires; `set_bowl_config` stays the expensive re-bake path and is never called per tick) — projection done per-VERTEX in the shader, not per-fragment (cheaper, and its fidelity is bounded by the same tessellation argument as the bake; the per-FRAGMENT distortion path is what this Decision rules out as unresearched, §7.5). The interpolant layout below is unchanged — `CUSTOM0`/`CUSTOM1` still carry `{u,v,weight,index}`, the u/v now computed per-vertex rather than fetched from an attribute. This is the "shader-side projection" alternative Decision 2 already flags as a USER DECISION at Task 2's review gate; that gate confirms or overturns it (the strawman it decides against: fully-static bake + a full CPU re-bake hitch every tick while driving), and now also decides whether ego-motion compensation, not just fidelity, is what forces shader-side. The K-rescale half of `rendering_node.cpp:762-767` (output/native resolution ratio) does **not** carry over: it exists only because the CUDA kernel resizes all six camera images onto one fixed NHWC canvas before projecting; this design samples each camera's texture at its native resolution via a normalized UV, so there is no output canvas to rescale K against. Task 2 Step 5's perf gate must include a "bowl + ego-motion uniform update, actively driving" case, not just a static bowl-on/bowl-off pair, and a live GUI extrinsics/bowl-radius slider drag is budgeted as a full re-bake hitch, acceptable up to one dropped frame (~33 ms) at the slider's own update rate — tighter than that requires the shader-side path above, not a silent tessellation tweak.

**bowl.mat's vertex→fragment interpolant budget is a hard Filament limit, not a tuning knob — and whatever fills it must survive linear interpolation, which rules out bit-packing.** `MaterialBuilder.h:214-220` fixes `MATERIAL_VARIABLES_COUNT = 4` (`Variable::CUSTOM0..CUSTOM3`) — 4 custom vec4 interpolants, 16 floats total, per material; `CUSTOM0..CUSTOM3` are vertex-to-fragment varyings, and the rasterizer linearly interpolates whatever float sits in each component across a triangle. Decision 3's naive per-camera (u, v, weight) × 6 cameras is 18 floats — over budget by 2 even before interpolation-safety is considered. (Vertex-*attribute* capacity is not the constraint: `MAX_CUSTOM_ATTRIBUTES = 8`, `MaterialEnums.h:158`, and `MAX_VERTEX_ATTRIBUTE_COUNT = 16`, `backend/DriverEnums.h:99`, both comfortably cover 18 floats of attributes — the wall is specifically the 4-variable *interpolant* budget between vertex and fragment stages.) **A packed/quantized scheme does not solve this — it looks like it fits and silently corrupts the blend instead:** interpolating a bit-packed float (e.g. two 8-bit weights via `packHalf2x16`-style packing) and unpacking it in the fragment shader does not yield the interpolation of the two packed values; it yields garbage that varies smoothly across the triangle and therefore reads as a plausible-but-wrong blend, uncaught by `matc` (which only validates the 4-variable budget, not what the packed floats decode to) and easy to miss against a golden that's "human-sanity-approved," not a numeric diff. **Bit-packed or quantized values must never be placed in a CUSTOM interpolant for this reason — full stop.** **Interpolation-safe layout (primary design, not a fallback):** a bowl vertex is realistically covered by at most 2 adjacent cameras at any seam (the CUDA reference's own feather blend only ever overlaps neighbors) — pass 2 × (u, v, weight) plus 2 camera indices = 8 floats = 2 plain `vec4`s (`CUSTOM0` = cam_a.{u,v,weight,index}, `CUSTOM1` = cam_b.{u,v,weight,index}), well inside the 4-variable budget with `CUSTOM2`/`CUSTOM3` spare. A vertex covered by only one camera sets `cam_b`'s weight to 0. **The index components are only safe under an explicit mesh-construction rule the bake must enforce — the covering camera *pair* changes around the bowl, and a triangle whose vertices disagree on which camera fills a slot would have the rasterizer linearly interpolate the indices into fractional garbage, exactly the plausible-but-wrong-blend corruption class bit-packing is banned for above.** The rule: camera-slot assignment is uniform per triangle. Assign slots by a canonical global order (e.g. ascending camera index → slot a/b), and at coverage boundaries split/duplicate vertices so all three vertices of every triangle carry the identical (cam_a, cam_b) index pair — a vertex a slot's camera does not cover carries that camera's index with weight 0. Weight and UV interpolate safely across such a triangle; an index never varies within one, so its "interpolation" is the constant. **Simpler alternative, also interpolation-safe, worth trying first per the ladder:** don't interpolate weights at all — the feather weight is a function of distance from the sampled UV to that camera's image border (`blend.cuh`'s own feather math), so compute it in the fragment shader from the interpolated UV directly; only the UVs and the 1-2 camera indices cross as interpolants at all. The same per-triangle-uniform-index construction rule holds for this shape too, since it also passes indices. Either shape replaces the bit-packing scheme entirely; the two-camera assumption is an implementer tessellation/coverage call to verify against the golden, same as the fidelity calls elsewhere in this Decision. Task 2 Step 3 (the Filament-free bake test) must assert the chosen layout's values round-trip correctly, that a linear interpolation of two baked vertices' raw weight floats reproduces the expected mid-edge weight — and, for the shader-computed UV (not a baked attribute, per the addendum above), that a host-side `ProjectToCameraUv` reference computation at the mid-edge position agrees with the endpoint UVs' linear interpolation to within the tessellation-bounded tolerance (the actual property bit-packing cannot have), *and* the seam case: a triangle spanning two adjacent cameras' coverage boundary comes out of the bake with identical index components at all three vertices (the construction rule above, exercised where it matters), and **Step 4 compiles `bowl.mat` through `matc` (`-a opengl -p desktop`, the same invocation `visual_renderer/CMakeLists.txt:133` already uses) before any mesh-generation code is written**, so an interpolant-budget violation is caught by the build, not by a later visual artifact. That same `matc` run must also prove the per-material *sampler* budget at the feature level this build actually targets: `MaterialBuilder.h:869` defaults `mFeatureLevel` to `FeatureLevel::FEATURE_LEVEL_1`, and `MAX_SAMPLER_COUNT = 62` (`backend/DriverEnums.h:100`, commented "Maximum needed at feature level 3") is a **feature-level-3 driver ceiling, not a per-material guarantee at FL1** — Filament reserves bindings for its own PBR/lighting passes on top of whatever a material declares. Either get `matc`'s own FL1 compile to prove 6 camera samplers fit in one `bowl.mat` (a real, checkable build-time fact, not an assumption carried over from the FL3 number), or collapse the 6 per-camera samplers to one `SAMPLER_2D_ARRAY` texture with depth = `camera_count`. **The array path carries its own constraint, stated rather than assumed: a 2D-array texture requires every layer to share one width/height, and nothing guarantees that — `BowlConfig` deliberately carries per-camera `cam_width`/`cam_height` arrays (Task 1's struct), filled from each camera's own `CameraInfo`.** `set_bowl_config()` validates: all `cam_width`/`cam_height` equal → array path; unequal → fall back to 6 discrete samplers (recorded in the results block — resampling to a common size is NOT taken, it would silently soften one camera's pixels). The array path also sidesteps a real shader hazard the 6-discrete-samplers path would hit: selecting a sampler by the varying-derived camera index is non-dynamically-uniform sampler indexing, undefined/ill-supported in GLSL — an array texture indexes by a layer coordinate instead, which is legal. Also verify `Texture::isTextureFormatSupported(engine, InternalFormat::RGB8)` (`Texture.h:89`) for the camera textures, falling back to RGBA8 if unsupported — RGB8's row alignment is a known soft spot on some GL backends.

**Exposure matching and blind-zone fill are deferred out of this migration, not silently dropped from `BowlConfig`.** Both are real, default-on algorithms in the CUDA node — `exposure_match` (default `true`, `rendering_node.cpp:88`, and `true` in the deployed `default_params.yaml`) collects GPU luminance statistics where neighboring cameras overlap and solves per-camera gains on the host in log space with a ridge anchor and 0.8/0.2 EMA smoothing, applied the next frame (`reprojector.cpp:97-181,436-444`); `fill_blind_zone` (default `true`, `rendering_node.cpp:79`, `fill_blind_zone: true` in `default_params.yaml`) propagates surrounding scene color into the uncovered ring around the robot before the robot overlay (`kernels/fill.cu`). Neither has a Filament-side implementation in this plan — the merged node's bowl would otherwise silently claim both capabilities (they are named fields on `BowlConfig`, Task 1) while actually rendering a zero-weight blind ring and un-matched seam brightness steps. **Decision: ship both flags declared but CLAMPED to `false` at the node — the merged node's param handling coerces any `true` to `false` with a WARN (Task 2) until a Filament-side implementation exists — not merely defaulted `false` in the shipped `default_params.yaml`.** A yaml-only rule would re-enable both on the first real robot config: the deployed `m2o1_params.yaml` carries both `true` (`m2o1_params.yaml:17-18`), and `autotune_config.py` emits `fill_blind_zone: True` (`:370`) while omitting `exposure_match` entirely, inheriting the old node's `true` declare-default (`rendering_node.cpp:88`) — so every generated config would silently claim the capability too. The clamp at the node is the root-cause guard covering every config source; belt-and-braces, Task 6 Step 2b's schema translation and its autotune rework also set both keys `false` explicitly. Record both as **named, user-visible parity exceptions** in Task 4 Step 1's checklist (visible seam-brightness steps between cameras; a visibly-empty ring around the robot instead of an inward-extrapolated fill) — not blocking parity sign-off unless the user says otherwise at that gate, since re-implementing either is materially new library rendering work (a stats pass + host solve, or a skirt mesh / screen-space extrapolation pass) that this epic's own risk-ranking (Decision 1) defers past first cutover.

### 4. Self-view masks + robot-proxy compositing: delete the kernels, don't port them

Research §1.11 already names the finding: robot-proxy compositing (`robot_raster.cu`, a hand-written z-buffer triangle rasterizer) does exactly what Filament's own scene renderer already does for free. The ego glTF mesh is **already** a Filament-native renderable (`set_ego_model()`, mode 3, shipped since Epic 1) — adding it to the **same** Filament `Scene` as the bowl mesh (Task 2) means Filament's own depth test composites robot-over-bowl correctly with zero new code. Self-view masking (hiding the robot's own body from smearing onto the bowl surface as seen by each real camera) is not a rasterizer problem either — it is "for each camera, don't trust bowl-vertex UV samples that the ego mesh would occlude from that camera's vantage." Decision: extend Task 2's per-vertex weight bake (Decision 3's addendum: UVs are shader-computed, weights/indices are what the bake produces) with an analytic occlusion test (ego bounding box vs. the camera-to-vertex ray) rather than a full per-camera depth-render pass — a deliberate fidelity/complexity simplification, named as such, with the golden comparison as the check that catches it if the box-test proves visibly wrong (Task 3's own review gate item).

**Self-view masks ship OFF by default, matching the CUDA node's own default, and the reason is load-bearing, not cosmetic.** `rendering_node.cpp:85` declares `self_view_masks_ = declare_parameter<bool>("self_view_masks", false)` — default **false** — and the comment immediately above it (`:80-84`) explains why: "OFF by default: correct masks require the rig origin to be exactly the body center — verify with the mask-overlay preview before enabling (a wrong origin masks REAL scene, which is far worse than the body smear it removes)." Task 3 ships this node-side occlusion test the same way: declared, off by default, keeping the CUDA node's exact param name `self_view_masks` — no rename to `self_view_masks_enabled`, so config/GUI parity holds against both the deployed yamls and the autotune generator without any extra plumbing.

**The default is also load-bearing for a second reason the CUDA node's own control flow makes explicit: masks and blind-zone fill are coupled, and this epic ships the one combination the CUDA node itself refuses to run.** `rendering_node.cpp:634` only generates self-view masks when `self_view_masks_ && !self_masks_done_ && have_robot_mesh_ && bowl_.fill_blind_zone` — mask generation is gated on `fill_blind_zone` being true. Why: `reprojector.hpp`'s `upload_self_masks()` doc (the comment directly above the declaration) says masked pixels "are skipped during bowl reprojection (the blind-zone fill then covers the region)" — a masked pixel is deliberately left with no bowl-reprojection color, on the assumption that the blind-zone fill pass will paint it. Decision 3 already clamps `fill_blind_zone` to `false` at the merged node (the exposure/blind-zone deferral — node-side coercion, not just the shipped `default_params.yaml`). If Task 3's occlusion test were ever turned on while blind-zone fill stays forced off, the masked vertices become *uncovered holes* — nothing paints them — a visual regression the CUDA node's own guard exists specifically to prevent, and neither Decision 3's nor Task 4 Step 1's named-exception lists currently anticipate this combination.

**Decision, stated once so Task 3 and Task 4 both carry it forward:** with `fill_blind_zone` forced false for this epic, self-view occlusion stays declared-but-off by default (same default as the CUDA node, for the same reason), and is documented as blocked on blind-zone fill landing — turning it on before then is a known-bad configuration, not a tuning choice. Task 3 Step 1's test must assert the off-by-default behavior; add a second assertion that a vertex the occlusion test zeroes out (when the knob is force-enabled for the test only) falls back to `sky_color` rather than being left unshaded, so the fallback path exists and is exercised even while the feature itself ships off. Task 4 Step 1's named-exception checklist gets this coupling added explicitly, citing `rendering_node.cpp:634` and `reprojector.hpp`'s `upload_self_masks` doc.

### 5. Mode 2 needs **zero** new library rendering code

Research §2's finding, restated as the actual design: mode 2's only genuinely new behavior versus mode 1 is colorizing lidar points from the synchronized camera images. That colorization is host-side math (project each lidar point into whichever camera's FOV covers it, using the **same** portable projection function Decision 3 ports in Task 2 Step 0, sample that camera's already-ingested raw image) producing exactly `mpviz::PointCloudPoint{position, rgba}` — the type **already in `scene.h`**, already rendered by the **already-shipped** `PointCloud` layer (VM-035, Epic 3 Task 6), and already reused verbatim once before for an unrelated producer (`TrajectoryCarpet` reusing `PointCloudPoint` per VM-077, `scene.h:171-180`). Mode 2 = mode 1's bowl (fallback, unchanged) + a new node-side adapter feeding an existing `SceneGraph::point_clouds` row. **`splat_radius` becomes vestigial — declared but not wired.** There is no mechanism to wire it: `update_point_clouds()` overwrites the `pointSizePx` uniform every frame from the live theme (`point_cloud.cpp:200-203`, sourced from `active_theme.point_cloud.point_size_px`), so a node-side param cannot reach it through any existing surface, and any real plumbing would either be a second `kSceneVersion` bump this epic's review gate forbids (a per-row size field on `PointCloud` — "Task 1's bump (4→5) is the only one this epic makes") or a new free function whose only job is to mirror a value the theme token already owns, failing the STANDING directive's style-is-theme-tokens rule. It stays declared because the GUI bridge's `TUNABLE_PARAMS` carries it (`vcam_ws_bridge.py:62-67`) and Task 6 Step 5's gate requires every `TUNABLE_PARAM` declared on the merged node — documented at the declaration as superseded by the theme token `point_cloud.point_size_px` (the STANDING directive's "style = theme tokens" rule; Decision 8's vestigial-but-named precedent). The GUI tuning panel's `splat_radius` row is inert post-cutover, noted at Task 6 Step 5. No new `SceneGraph` category, no new entry point beyond what Task 2 already added.

**Correction to an earlier draft's citation:** `reprojector.hpp:30-36` does **not** say the CUDA node's own colorization is first-match/unblended — it documents the opposite: lidar points are colorized **on device from every already-uploaded camera image, distortion-aware and feather-weighted, "same blend as the bowl kernel"**, and a point no camera covers is **dropped by the splat pass**, not emitted with a neutral/zero-alpha color. First-match-not-blended, and emitting uncovered points as visible theme-neutral dots (`a == 0`, resolved by `point_cloud.cpp:112-121`'s `resolve_rgba`), is therefore a real fidelity regression versus the CUDA reference, not "matching" it — Task 5's design below is re-argued on that corrected basis, not on a false parity claim.
